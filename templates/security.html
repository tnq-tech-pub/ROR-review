This page describes how the Affiliation Review application approaches security and compliance. The Tool is an independent community contribution supporting the ROR ecosystem and is not an official ROR service.

1. Scope

This statement covers:

  • The Affiliation Review web application (Flask UI and processing workflow)
  • Local or server-side storage of batch results, remarks, verifications, and insertion exports
  • Outbound calls to the public ROR API for affiliation matching

2. Data handled

  • Affiliation strings you paste or upload (TXT/CSV)
  • Review metadata such as comments, verification outcomes, and insertion drafts
  • Match results returned by the ROR API (organization candidates, scores, identifiers)

Avoid uploading sensitive personal data that is not required for affiliation matching. Operators of a deployment are responsible for configuring appropriate retention and access controls on the host environment.

3. Storage and transmission

  • Results are stored as filesystem artifacts (JSON batches and CSV/XLSX exports) under the configured output directories for that deployment.
  • Concurrent CSV writes use file locking to reduce corruption risk when multiple workers are active.
  • Deployments should be served over HTTPS in production so browser traffic to the Tool is encrypted in transit.
  • ROR API requests are made over HTTPS to api.ror.org / ROR documentation endpoints.

4. Access control

By default, the application does not include end-user authentication. If you deploy the Tool in a shared or production environment, restrict access using network controls, reverse-proxy auth, VPN, or SSO in front of the service.

5. Dependencies and updates

The Tool uses a small Python stack (Flask, Gunicorn, requests, openpyxl). Operators should keep base images and dependencies updated and review ROR API documentation for changes that may affect matching behavior.

6. Compliance posture

  • Not an official ROR processing pipeline. Outputs support human review and do not bypass ROR curation.
  • Licensing: application source under MIT; ROR data under CC0 1.0.
  • Privacy: see the ROR Privacy Policy for application privacy practices.
  • Brand use: ROR logo and identifiers must follow ROR display guidelines.

7. Incident and responsible use

If you discover a security issue in a deployment of this Tool, notify the deployment operator and, where appropriate, TNQTech through channels listed on tnqtech.com. Do not publicly disclose exploit details before a reasonable remediation window.

8. Operator checklist

  • Terminate TLS at a reverse proxy or load balancer
  • Limit who can reach the UI and download endpoints
  • Back up and rotate ror_results data according to your retention policy
  • Monitor ROR API usage against current ROR REST API rate limits and client ID guidance (values may change; always follow ROR’s published docs)
